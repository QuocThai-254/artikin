## 2. Harness loop — how this project is driven

```
 ┌─────────┐   ┌──────────┐   ┌─────────┐   ┌────────┐   ┌────────┐   ┌────────┐
 │  PLAN   │──▶│ DISPATCH │──▶│ EXECUTE │──▶│ VERIFY │──▶│ RECORD │──▶│ DECIDE │──┐
 └─────────┘   └──────────┘   └─────────┘   └────────┘   └────────┘   └────────┘  │
      ▲                                                                            │
      └──────────────────── fix tasks / next milestone ◀───────────────────────────┘
```

| Step | Who | What |
|---|---|---|
| PLAN | Supervisor | Keep PROJECT/ARCHITECTURE current; break milestones into tasks with acceptance criteria (this board). |
| DISPATCH | Supervisor | One session per workstream with a kickoff prompt, ownership area, port/dist-dir/PGlite dir. |
| EXECUTE | Agent | Implement in small vertical steps; keep the app building; respect ownership & concurrency rules. |
| VERIFY | Agent, then Supervisor/QA | Agent runs the gate commands and captures screenshots; supervisor (or the QA session) independently re-checks. |
| RECORD | Agent | Update task rows (status + evidence), work log, handoff notes, ARCHITECTURE sections. |
| DECIDE | Supervisor | Accept → next milestone; reject → add a `🔁` fix row and send it back to the owning session. |

A task is **done** only with evidence: commands run and their result, test names, screenshot paths,
or a reviewer's confirmation. The loop repeats until release gate **G5** passes.
